# AGENTS.md — BANYU_ROBOTX

ROS 2 Jazzy underwater ROV autonomy stack: ArduSub SITL + Gazebo Harmonic + MAVROS + BehaviorTree.CPP mission manager. The workspace root is the colcon workspace containing this repo; ArduPilot source (non-ROS, read-only reference) is a separate checkout (e.g. `~/ardupilot`). Paths and package names below are relative to the workspace.

## Architecture (non-obvious wiring)

### Refactored dual mission implementation reference

- `banyu_bringup/launch/mission.launch.py` is the mission-stack entrypoint. Select exactly `mode:=por` or `mode:=task2`; it passes the POR profile (`por_params_file`, default `por_params_timed_safe.yaml`) or `task2_params.yaml` to the mode's nodes. POR has only three profiles: `por_params_timed_safe.yaml`, `por_params_timed_fastest.yaml`, `por_params_replay.yaml`. RC vs no-RC is never a profile setting: `launch_por.sh --no-rc` passes `bypass_rc:=True` (plus teleop off, ESP32 trigger on); do not reintroduce `_no_rc` twins. `main_launch.launch.py` remains the full Gazebo/SITL composition entrypoint. `sub_bringup.launch.py` is the physical ROV bringup entrypoint (launches `usb_cam` cameras (front "H264 USB Camera", bottom Horus B "2M WebCam"), `banyu_teleop` safety switches, and `mission.launch.py`).
- **POR wiring:** `banyu_mission/banyu_mission` loads `bt/por_timed_mission.xml` by default (`mission.use_vision: false`), `bt/por_mission.xml` with `use_vision: true`, `por_vision_assisted_mission.xml` with `use_vision_assist: true`, `por_hybrid_mission.xml` with `use_vision_return: true` or `por_replay_mission.xml` with `use_replay: true` (teach & replay: `ReplayTrackServer` replays a manual drive cut from a bag by `tools/scripts/por/por_teach_extract.py`, track picked by the `replay_track` launch argument; sticks come from `/mavros/rc/in`, or, without an RC receiver (Pixhawk then reports no RC channels), from the QGC joystick `MANUAL_CONTROL` in the per-session MAVProxy tlog that `run_mavproxy.sh` writes to `~/banyu_bags/mavproxy/`); `banyu_detection/por_detection` publishes target detections; `banyu_vehicle_execution/vehicle_execution_node` provides the vehicle action servers (`por_action_servers` and `TimedMoveServer`) and setpoint bridge; `banyu_vehicle_interface/vehicle_status_node` publishes vehicle status. These four nodes are launched in `por` mode.
- **Task 2 wiring:** `banyu_mission/banyu_mission` loads `bt/banyu_mission.xml`; `banyu_detection/task2_pipeline_detector`, `ring_tracker_node`, and `pipeline_end_node`, `banyu_guidance/pipeline_guidance_node`, `banyu_vehicle_execution/vehicle_execution_node`, `banyu_vehicle_interface/vehicle_status_node`, `banyu_detection/survey_evidence_node`, `banyu_vehicle_execution/calibrated_depth_node`, `banyu_communication/uuv_comm_node` (RobotX SoS interface), `banyu_communication/pipeline_buoys_node` (USV buoy feed) are launched in `task2` mode. `test_mission:=True` (`launch_task2.sh --test-mission`, overlay `config/task2_test_mission.yaml`, `mission.strategy: test`) loads `bt/task2_test_mission.xml` instead: same run start, USV buoys and midpoint dive point (`dive_point: midpoint`), then GPS transit with keep-out, `AlignHeading` to the end buoy, `TimedMove` dive to 1 m and timed forward/backward legs, surface, best-effort Core report; `tools/scripts/run/task2_test_waypoint.py` sends course, start and the buoys (`docs/task2_test_mission.md`). **The competition UUV has no hydrophone:** `use_hydrophone` (default `False` in `mission.launch.py`, `main_launch.launch.py`, `sub_bringup.launch.py`; `launch_task2.sh --hydrophone`) gates `banyu_detection/pinger_localization` (hydrophone TDOA → `/banyu/pinger/observation`), the sim `HydrophoneArray` plugin and its bridge, and every pinger reader (`SearchPipeline` homing, `underwater_odometry_node` bearing corrections, the sim provider's fake heading) through `config/task2_hydrophone_on.yaml`. With it off `SearchPipeline` retraces and sweeps only and the start buoy comes only from the USV `PipelineBuoys` (GREEN). `Course.pinger_freq_hz` is a report field, not a sensor: keep it. `banyu_bringup/task2_sim_provider.py` is additionally launched only for `mode:=task2 use_sim:=True` as the deterministic fixture source.
- Vehicle execution is implemented and launched in both modes. It owns the action servers and consumes the relevant detection/pipeline/guidance inputs, arbitrates commands, and publishes `/banyu/execution/preview_target` plus `/mavros/setpoint_raw/local` when enabled.
- **POR vision BT flow** (`bt/por_mission.xml`, `use_vision: true`; the default timed tree runs `TimedMove` legs instead): interrupt/abort handling; `RequireMissionStarted` → `ArmAndSetGuided` → acquire and align the gate → pass it → search/align/orbit the marker → turn around → search/align/pass the gate on the return leg → surface.
- **Task 2 BT/pipeline flow** (`bt/banyu_mission.xml`): interrupt/abort handling; preflight → surface GPS transit and heading alignment → dive/acquire pipeline → traverse while following, repairing red rings, and reacquiring after loss → surface and publish the pipeline survey. The pipeline is detector → observations/ring tracker → guidance velocity intent → vehicle execution; `pipeline_end_node` supplies the end signal (the sim fixture's ground-truth end candidates, or, the only signal on the robot, four rings recorded with no RED waiting for its repair (`ring_tracker` `/banyu/pipeline/rings_complete`) and the pipe out of view for `rings_complete_lost_s`), `survey_evidence_node` assembles the survey, and `uuv_comm_node` publishes the public `rx_msgs` reports.
- **Task 2 surface transit and dive point:** the surface goal is at least `mission.buoy_standoff_m` (1.5 m) inside the start buoy (`dive_point:=buoy`) or midway between the buoys (`dive_point:=midpoint`, the default; `auto` = midpoint for every strategy; `--dive-point buoy` dives inside the start buoy); `NavigateSurfaceGps` keeps `mission.buoy_keep_out_m` (1.2 m, below the standoff) clear of both `PipelineBuoys` buoys (a detour point beside a buoy in the way, re-checked every tick), `gps_tolerance_m` 0.4 keeps the dive on the buoy line, and `AlignHeading` holds its GPS position while turning. It also detours round fixed surface obstacles (`banyu_msgs/SurfaceObstacles`, `/banyu/surface/obstacles`, per `source`): today the UAV's Task 1 buoy field, which `pipeline_buoys_node` turns from `rx_msgs/SafePassage` (`/system/vehicle/uav/task1/safe_passage`, `uav_buoys.radius_m`, course-filtered); a circle around the dive point is dropped. They are not Task 4 zones (no surface hold). After the dive both modes back up along the pipe (`FollowPipeline reverse`) to its start, then survey forward; rings are recorded only in that forward pass (`SetRingRecording`, `/banyu/mission/ring_recording`); the report order is the order of first sighting in that pass (`frame_sequence`). There is no pipe map and no underwater position: `ring_tracker` dead-reckons from the last surface fix and its progress along the buoy line only tells a repeat sighting from a new node. Do not reintroduce a hard-coded pipe centerline. **Light cue:** with no pipe in view `task2_pipeline_detector` publishes a RED or GREEN light (the only colours before the repair) seen anywhere in the image on `/banyu/pipeline/light_cue` (its own topic: never a ring record), and `AcquirePipeline`/`SearchPipeline` steer over it (the node sits on the pipe) instead of driving on, retracing or sweeping; ignored above `light_cue.min_depth_m` (the start buoy's indicator) and after `light_cue.budget_s` per goal; they still succeed only on a tracked pipe.
- **Task 4 keep-out zones (Dynamic Incident Response, Advanced + Disruptive; `docs/task4.md`):** a surfaced UUV is a USV, so entering a RoboCommand zone costs -25. `uuv_comm_node` (`Task4ZoneTracker`) keeps the static `CMD_TASK4_KEEP_OUT_ZONE` circles until `CMD_TASK4_ALL_CLEAR` and the latest `CMD_TASK4_MOVING_OBJECT` (compass heading → ENU), accepts TYPE_UUV/UNKNOWN/USV targets (ack only the first two, `IncidentAck`; MOVING_OBJECT ack off by `task4.ack_moving_object`), dedups by `(command_seq, command_type)`, clears at the PREPARING lifecycle (prepare_autonomy) and publishes `banyu_msgs/Task4Zones` on `/banyu/task4/zones` (1 Hz + on change, transient_local, recorded). `vehicle_execution_node` (`zones.*`, geometry in `task4_zones.hpp`) turns it into capsules (static circle; moving object swept over `zones.horizon_s`, both inflated by `zones.margin_m`) and, in velocity setpoints only: `NavigateSurfaceGps` leaves a zone first, detours round zones on the path every tick, shifts a dive point inside a static zone along the buoy line (then anywhere) and waits at the edge of a moving object's projected zone; `AlignHeading` moves out and holds outside; with no goal running (`WaitForBuoyTarget` standby, after the report) the idle guard does the same; `Surface` with `hold_for_zones` waits at depth (`zones.surface_hold_timeout_s`, last GPS fix as the position) while the surfacing point is inside a zone, then ascends anyway; the BT's final `KeepClearOfZones` keeps the mission (and the vehicle armed) on the surface while a zone is active. Abort/teleop surfacing is not delayed. `tools/scripts/run/task4_command.py` sends the commands.
- Key contracts: `/banyu/mission/start` and `/banyu/mission/abort` are `std_srvs/srv/Trigger`; ring repair is `/banyu/pipeline/acknowledge_ring_repair` (`banyu_msgs/srv/AcknowledgeRingRepair`). POR uses `/banyu/detection` (`Detection`, one best target per frame; object `0` gate, `1` yellow buoy). Task 2 uses `/banyu/pipeline/observation`, `/banyu/pipeline/ring_observation`, `/banyu/pipeline/ring_state`, `/banyu/pipeline/accepted_ring`, `/banyu/guidance/velocity_intent`, `/banyu/pipeline/end`, and `/banyu/vehicle_status`. POR actions are `/banyu/actions/{acquire_gate,search_marker,search_gate,align_gate,align_marker,pass_gate,orbit_marker,turn_around,surface}`; Task 2 uses the navigation/pipeline action family (`navigate_surface_gps`, `align_heading`, `dive_to_depth`, `acquire_pipeline`, `search_pipeline`, `follow_pipeline`, `center_on_ring`, `hold_probe_on_ring`, `surface`) Task 2 does not start from `/banyu/mission/start`: the operator calls `/banyu/mission/prepare_autonomy`, then the run starts only on a GCS `CMD_RUN_START` (`/system/mission/command`).
- POR and Task 2 detectors are distinct: `por_detection` is the HSV target/`Detection` path, while `task2_pipeline_detector` detects pipeline and ring observations from the configured Task 2 camera topics; Task 2 does not use `por_detection`.
- **Implementation rule:** whenever a ROS node declares or adds/renames a parameter, update that node's matching section in every `banyu_bringup/config/por_params_*.yaml` or `task2_params.yaml`, ensure `mission.launch.py` passes it in the relevant mode, and update launch wiring, installation, and package dependencies when adding a node. If the change touches anything an operator sets per run, also update the operator launch script (see [Operator launch scripts](#operator-launch-scripts)).

- Packages: `banyu_bringup` (launch + config), `banyu_simulation` (worlds/models), `banyu_teleop` (RC switch handling: unified Pixhawk arming and ESP32 kill switch on `SB`, flight mode on `SC`, `SF` unmapped; single source of truth is `banyu_teleop/config/teleop_rcin.yaml`), `banyu_msgs` (mission/perception contracts), `banyu_mission` (BT mission manager), `banyu_detection` (POR target and Task 2 pipeline/ring/survey detectors), `banyu_guidance` (pipeline velocity intent), `banyu_vehicle_interface` (vehicle telemetry/status), `banyu_vehicle_execution` (action servers, arbiter, velocity setpoint bridge), `banyu_communication` (RobotX SoS & USV buoy interfaces).
- Camera: gz topic `front_camera/image_raw` → `ros_gz_image image_bridge` → ROS `/front_camera/image_raw` (30 Hz). `camera/camera_info` is NOT bridged. Never modify the `front_camera` sensor block in `bluerov2_gz/models/bluerov2_heavy/model.xacro` — user-configured.
- **Visual centering & crosshairs:** The red crosshair in `por_detection` is drawn strictly at the camera image center (`cols / 2`, `rows / 2`) as the vehicle bore reference; detected object centroids are drawn with bounding boxes/circles. Visual alignment actions (`AlignGate`, `AlignMarker`) and `OrbitMarker` drive normalized image offsets `(offset_x, offset_y)` toward zero. During hold times, alignment actions continue commanding centering velocities rather than stopping at the deadband edge.
- **Orbit feedforward yaw rate:** `OrbitMarker` must apply a feedforward yaw rate $\omega_{\text{ff}} = -\frac{y}{\text{radius}}$ alongside feedback yaw rate. Pure P-gain visual feedback suffers steady-state tracking lag under continuous tangential sway velocity $y$, leaving the marker visibly shifted off the center crosshair.
- **PassGate blind push:** On the return leg, losing gate detection enters `blind_mode_`, logs `"Executing: PassGate Detection Lost, Continue pushing through"`, and pushes forward until bounded blind duration or target distance is completed. Reacquiring detection resets blind mode.
- Frames: Gazebo and MAVROS ROS pose/setpoint fields are **ENU** (`/mavros/local_position/pose` uses `frame_id: map`); MAVROS converts local `PositionTarget` fields to MAVLink NED internally. The `coordinate_frame` constants are still MAVLink values. Convert mission NED offsets explicitly: east→ROS x, north→ROS y, down→negative ROS z.
- **POR flies ALT_HOLD + RC override, not GUIDED.** Every `por_params*.yaml` sets `autonomy_mode: "ALT_HOLD"` in `banyu_mission`, `vehicle_execution_node.control` and `banyu_vehicle_status`, with `control.output_mode: "rc_override"` (velocity intents → `/mavros/rc/override` sticks; `rc_override.channel_*` must match Pixhawk `RCMAP_*` and must not be a `banyu_teleop` switch channel: `/mavros/rc/in` reports override values, so an override on the SB channel reads as an SB move; `launch_por.sh --real` refuses the overlap). The GUIDED/setpoint notes below apply to Task 2. Operator docs: `docs/por/` (README = run and profile choice, tuning.md, sim_results.md). `vehicle_execution_node` owns the sticks only while a goal runs and for `rc_override.idle_release_s` (2 s) after it, then releases them: armed in ALT_HOLD with no mission (e.g. a manual teach drive) it must never stream neutral overrides over the pilot.
- **Navigation is velocity-loop, not position-setpoint.** ArduSub GUIDED `0xDF8` position targets go through AC_WPNav, which in this SITL setup crawls and lets depth drift — verified empirically. Vehicle-execution navigation and mission actions run P-controllers and stream velocity-only setpoints (`type_mask 0x5C7`, ROS ENU components). Velocity-only control holds depth precisely. Keep `0xDF8` for reference only.
- **Every setpoint must carry an explicit zero yaw rate** (type_mask clears IGNORE_YAW_RATE, `yaw_rate = 0`). ArduSub persists `yaw_look_at_heading_slew` from the last commanded yaw rate and applies it in the guided-velocity LOOK_AT_HEADING branch, so a setpoint that merely ignores yaw rate leaves the vehicle rotating toward heading 0. `bodyVelocityYawRateSetpoint` overrides the field for turns/orbits.
- `AcquireGate` defaults to a dive in place: horizontal movement here would put the sub above the gate and risk collision on descent. Forward motion belongs to `PassGate`.
- ArduSub accepts `setpoint_raw/local` **only in GUIDED**, and setpoints must stream continuously (~10–50 Hz), not once. When the sim misbehaves, check for stale processes: `sim_vehicle.py`'s `ardusub` child and `mavproxy` can outlive their launch (orphaned from old terminals); a clean test requires killing ALL of them first or the new `ardusub` fails to bind port 5501 and the gz plugin logs `ArduPilot controller has reset`.
- Ports: MAVROS on `udp://127.0.0.1:14551`, SITL exports `14550` for QGC (works fine as a second GCS). In GUIDED, ArduSub ignores MANUAL_CONTROL RC overrides. `banyu_teleop` aborts through SB instead: SB Mid sets MANUAL (operational_mode 1), SB Down sets kill (operational_mode 0) and disarms.
- Setpieces: Gate at x≈−4 (posts Y=±1), `yellow_buoy` at x≈6 z≈−2.1, sub spawns at the surface (−7, 0, −0.1) because ArduSub zeroes depth on arming. `mav.parm` at workspace root is an auto-dumped param reference.

## RobotX SoS interface and simulation (Issue #13)

- Public UUV ⇄ GCS contract is `/system/...` with `rx_msgs` (team repo `RobotX-SoS-communication-ITSN`); UUV domain 40, GCS domain 10; only `/system/*` crosses. GCS-side bridge spec: `docs/gcs_ros_bridge_spec.md`; one-machine end-to-end tools: `tools/sos_integration/`. Status and evidence: `docs/issue13.md`.
- RoboCommand numbers `RxCommand.seq` per session and its host console can reset run ID and seq to 1 between runs ("Reset run ID & seq"). `prepare_autonomy` therefore opens a new run identity window: the accepted `run_id`s and the highest seq are forgotten, while the epoch keeps increasing. Anything per run that must survive a reused `run_id` is keyed by epoch (report seals, `uuv_comm_node` submitted reports, report ids). Within one window, duplicate and replayed starts are still ignored.
- Task 2 buoys (issue #16): the USV publishes `rx_msgs/PipelineBuoys` on `/system/vehicle/usv/task2/pipeline_buoys` and the GCS forwards it to domain 40. `pipeline_buoys_node` validates it (course_id, `TYPE_USV`, newest seq, inside the course, finite values) and publishes `/banyu/task2/buoy_target` (`banyu_msgs/Task2BuoyTarget`, only once the active buoy is known) plus a run-tagged, GREEN-confirmed `ActiveBuoyFix` (source `usv_pipeline_buoys`) at 1 Hz during a live run. It locks for the run once calibrated depth exceeds `lock_depth_m` or the survey completes, and unlocks between runs. The mission writes the target into the blackboard (`target_latitude/longitude`, `heading`, `heading_prior`) until the BT's `LockBuoyTarget` (after `NavigateSurfaceGps`), and `NavigateSurfaceGps` re-sends its goal when the target moves more than `retarget_threshold_m`. There is no fallback to the YAML `mission.target_*` coordinates: after the run start the BT's `WaitForBuoyTarget` stands by on the surface, with no time limit, until the USV target arrives (the operator aborts to stop).
- **Simulation time:** Gazebo `/clock` is bridged and `SetParameter(use_sim_time)` (not `SetUseSimTime`, which only configures launch's own node) applies sim time to every launched node and MAVROS, only when `use_sim:=True`. Never mix wall-time nodes with sim-stamped sensors: the mission drops observations older than the run start.
- **ESP32 kill switch (firmware `indikator_banyu.ino`):** the board has no relay; it drives MANUAL/AUTO/EMERGENCY LEDs and senses the physical kill input (which cuts thruster power in hardware). Wire protocol: newline-terminated `its0` (manual), `its1` (auto), `its2` (emergency); it reports `itsN` every 500 ms and ignores `its0`/`its1` while the physical kill is active. Inside ROS the encoding stays `VehicleStatus.operational_mode` (issue #15: 0 kill, 1 manual, 2 autonomous); `banyu_teleop` (`esp32_indicator.hpp`), `esp32_trigger_node`, `esp32_bridge_node`, `esp32_kill_cmd.py` and `mock_esp32.py` map 0/1/2 ↔ its2/its0/its1. A board `its2` while 1/2 is commanded = physical kill: teleop disarms and holds kill while it is pressed, keeps sending the SB mode (never `its2`, or the release could not be seen) and returns to the current SB position on release; with RC lost at the release (`rc_timeout_s`) it holds until SB Down (trigger node: until a `'0'`).
- **YOLO runs on the Hailo-8** (PCIe accelerator on the Pi, HailoRT 4.24): `.hef` models only (compiled on x86 with the Hailo DFC), Python env `~/venv-yolo` (system site packages, numpy < 2 for `cv_bridge`). Setup `tools/scripts/setup/yolo_setup.sh`, test `tools/scripts/check/yolo_test.sh`, details `docs/hardware_setup.md` §8. The front camera is mounted upright (no rotation); only bags from before 2026-11-10 hold a sideways image.
- **No DVL, anywhere:** the AUV has no DVL and the sim has none either (the DVL sensor, bridge, `use_dvl` and `ekf_source_switch` were removed). Without GPS (`use_gps:=False`, POR) `nogps_odom_beacon.py` selects EKF3 source set 2 itself (`MAV_CMD_SET_EKF_SOURCE_SET`, resent every 5 s) and streams zero-delta `VISION_POSITION_DELTA`, so `/mavros/local_position/pose` carries depth + heading only. Its EKF velocity is always ~0: never use it for GUIDED velocity control. Do not reintroduce DVL paths.
- **Headless SITL deadman:** ArduSub SITL reports zero RC channels, so `rc_fresh` is never true from `/mavros/rc/in`. With `use_sim:=True`, `mission.launch.py` points `banyu_vehicle_status` `rc_topic` at `/sim/supervisor_rc` and starts `sim_rc_deadman_node`, which publishes it; `tools/sos_integration/sim_supervisor.py` is only needed for its lifecycle log. Never on hardware.
- Calibrated depth is `datum − rel_alt`, with the datum captured at the surface before each run (`calibrated_depth_node`). The sim EKF baro drifts 0.1–0.4 m, so surfaced checks use 0.5 m, and a pre-start datum is kept at the run start while the vehicle is still at the surface relative to it.
- `sim_vehicle.py` runs MAVProxy with `--streamrate=25` (sim time): the default 4 Hz pose is too slow for the mission's 1 s pose freshness check, and at 0.34x real time (iGPU) 10 Hz still left pose gaps past vehicle execution's 0.5 s hold freshness, which latches the readiness off until the next prepare. On the robot QGC's own `REQUEST_DATA_STREAM` (sent when it connects, after MAVProxy's `--streamrate=10`) cuts the pose to ~3 Hz with gaps up to 0.7 s, so `task2_params.yaml` sets `vehicle_execution_node` `control.pose_timeout_s: 1.0` and `banyu_mission` `timing.readiness_pose_timeout_s: 2.0` (defaults 0.5 / 1.0); RC override readiness holds (neutral sticks) need no pose.
- `task2_sim_provider.py` (sim only) also stands in for the USV and the missing end-of-pipe detector: `rx_msgs/PipelineBuoys` from the world's start (active) and end buoys (`start_buoy_map_*`, `end_buoy_map_*`), and run-tagged `PipelineEndCandidate` from ground truth (`pipeline_*_map_*` params). The active buoy evidence then comes through `pipeline_buoys_node`, as on the course.
- On PRIME on-demand laptops run Gazebo with `__NV_PRIME_RENDER_OFFLOAD=1 __GLX_VENDOR_LIBRARY_NAME=nvidia`, otherwise camera rendering falls back to the integrated GPU.
- About one launch in three the Gazebo GUI never hands the world to the server (`/gazebo/starting_world` stays, no "Received world"); relaunch.

## Build / run (shell is zsh!)

- ROS `setup.bash` uses `BASH_SOURCE`, which is unset in zsh → sourcing it resolves the prefix to CWD and errors. Always run ROS commands via: `bash -c 'source /opt/ros/jazzy/setup.bash && source install/setup.bash && <cmd>'` (from workspace root; install is symlink-install).
- Focused dual-architecture build: `colcon build --packages-select banyu_msgs banyu_guidance banyu_vehicle_interface banyu_vehicle_execution banyu_communication banyu_mission banyu_detection banyu_bringup` (from workspace root; build `banyu_msgs` before dependents).
- Unit tests: `banyu_vehicle_execution` has gtest coverage (`build/banyu_vehicle_execution/test_vehicle_execution`). When running tests while simulation/bringup nodes are active on the host, always isolate the DDS domain (e.g. `ROS_DOMAIN_ID=42 ./build/banyu_vehicle_execution/test_vehicle_execution`) to prevent live vehicle pose or status traffic from leaking into test fixtures and failing watchdog assertions.
- Mission launch: `ros2 launch banyu_bringup mission.launch.py mode:=por` or `ros2 launch banyu_bringup mission.launch.py mode:=task2`; full-sim launch-description sanity check: `ros2 launch banyu_bringup main_launch.launch.py --show-args`.

## Operator launch scripts

Operators launch runs through wrapper scripts, not raw `ros2 launch`: `tools/scripts/por/launch_por.sh` (symlinked at the workspace root) for POR in sim and on the real AUV. Task 2 uses `tools/scripts/run/launch_task2.sh`, built the same way, and every rule here applies to it too; sim batches run through `tools/scripts/sim/task2_sim_batch.sh` (starts MAVROS itself).

- **Script layout:** `tools/scripts/` is grouped by function (index: `tools/scripts/README.md`): `run/` (MAVProxy, MAVROS, GPS bridge, launchers), `check/` (health checks, `test_hardware.sh` bench test), `debug/` (one device by hand: cameras, kill lamp, ESP32 tools), `setup/` (one-time installs, RTK rover), `por/` (finished POR tools), `sim/` (simulation-only runs and experiments). Put new scripts in the matching folder; scripts locate the repo as `$(dirname script)/../../..`. Every script must answer `--help` without side effects (`setup/` scripts install things when run).

- **Keep the script in sync in the same change.** When you add, rename, remove or change the default of something an operator chooses or checks per run, update the script with it. Examples: a launch argument in `sub_bringup.launch.py` / `main_launch.launch.py` / `mission.launch.py`, a profile or params file, a device or port, a safety precondition, a mission feature toggle. Do not leave it for a later change.
- **What to update in the script:** argument parsing, the `--help` text (with an example if useful), the banner (operators read it right before a dive), `LAUNCH_CMD`, pre-flight checks or refusals, and the post-launch operator instructions. Then update the operator docs (`docs/por/README.md`, `banyu_bringup/README.md`).
- **Flags vs. profiles:** only per-run operator choices become flags (target, profile, RC / no-RC, cameras, recording, GPS, safety overrides). Tuning values belong in the YAML profiles, not in new flags.
- **Defaults:** keep the script's defaults the same as the launch file's, and safe for real hardware. Dangerous settings must be opt-in with an explicit `--allow-*` flag (like `--allow-channel-overlap`). A launch argument that is passed through but has no flag should still show up in the `--dry-run` command.
- **Verify** with `--dry-run` for `--sim` and `--real` and every new flag before finishing. The hardware checks only warn in dry-run mode, so this works on a laptop.

## Mission recording (no link underwater)

- The AUV loses all comms once submerged, so `sub_bringup.launch.py` records every real run (`record:=True`, `record_images:=True` by default) using `banyu_bringup/scripts/record_mission.sh`. Bags go to `$BANYU_BAG_DIR` (default `~/banyu_bags`) as `<YYYYmmdd_HHMMSS>_<label>/{bag/,run_info.txt,params/}`: MCAP, zstd, split every 60 s, raw images excluded, hidden action topics included. `launch_por.sh --real` exposes `--no-record` / `--no-record-images` and labels runs `por_<profile>` through `BANYU_BAG_LABEL`. Sim runs record only with `launch_por.sh --sim --record` (`main_launch record:=True`, sim time, label `por_<profile>_sim`); the POR sim adds Gazebo ground truth `/sim/ground_truth/odom` (OdometryPublisher injected into the spawned model in `gazebo_por.launch.py`), which `tools/scripts/por/por_path_compare.py` uses to compare a replay with its teach run. A replay run's folder also holds the flown track (`params/*.csv`, via `BANYU_BAG_REPLAY_TRACK`).
- Helpers started by launch must receive its signals: run scripts directly (`ExecuteProcess` with the installed path), never via `ros2 run`, which only forwards to a wrapper and orphans the child (this left `nogps_odom_beacon` instances running after every shutdown).
- After a power cut the bag has no `metadata.yaml`; `recover_bag.sh <run>/bag` moves truncated `.mcap` files into `partial/` and reindexes.
- The recorder is run directly (not via `ros2 run`) and sends SIGTERM to `ros2 bag`, because a background job in a non-interactive shell ignores SIGINT. Keep it that way, or bags won't close on shutdown.
- Anything needed to judge a run after the dive must be published on a ROS topic (it is recorded automatically); a live GUI or terminal output alone is lost underwater. `/rosout` is recorded.

## Mission manager gotchas (`banyu_mission`)

- Uses **core `behaviortree_cpp`** (apt `ros-${ROS_DISTRO}-behaviortree-cpp`, headers at `/opt/ros/${ROS_DISTRO}/include/behaviortree_cpp`). `behaviortree_ros2` is unnecessary — do not add it. (Note: On Humble, a multiarch symlink `libbehaviortree_cpp.so` was needed; Jazzy provides this out of the box).
- BT4 API differs from v3: `NodeStatus` is `enum class`; `BehaviorTreeFactory` has **no `setup()`**; register with `factory.registerNodeType<T>("ID", extraArgs...)`; run via `tree.tickWhileRunning()` in a `std::thread`; Groot2 monitor via `Groot2Publisher` (default port param 1666).
- `shared_from_this()` in the ctor throws `bad_weak_ptr` — `BanyuMission` uses two-phase init: `main()` calls `node->initialize()` after `std::make_shared`.
- The selected tree is `por_mission.xml` for POR or `banyu_mission.xml` for Task 2. Both use a reactive interrupt branch over a plain memory `Sequence` for mission phases; see the implementation-reference flow above. `AbortedOrTeleop` reacts to `/banyu/mission/abort`.
- **Do NOT use `ReactiveSequence` for the phase chain.** BT 4.9 `StatefulActionNode::tick()` calls only `onStart()` on the first tick and `onRunning()` on later ticks; `ReactiveSequence` re-ticks from the first child every tick and halts non-running siblings, so any action after the first never reaches `onRunning` and the chain loops forever. Plain `Sequence` (memory of the running child) works; abort reactivity is provided by the root `ReactiveFallback`.
- BT nodes use registered action clients and mutex-protected `MissionState` snapshots rather than blackboard sensor data. `/banyu/detection` is the POR contract: one best Detection per frame; `object_id` 0=gate, 1=yellow buoy; `offset_x/y` normalized ±1, +y = image-down.

## Repo-specific build/launch traps

- `banyu_msgs/package.xml`: `<member_of_group>rosidl_interface_packages</member_of_group>` must be a **top-level** element, NOT inside `<export>` — `package_xml_2_cmake.py` only fills `MEMBER_OF_GROUPS` from top level, otherwise `rosidl_generate_interfaces` fails.
- **No launch file starts MAVROS.** It runs on its own from `tools/scripts/run/launch_mavros.sh` (`--sim` for sim time; robot order: `run_mavproxy.sh` → `run_gps_bridge.sh` (GPS forwarder, `GPS1_TYPE 14`; Task 2) → `launch_mavros.sh` → `launch_por.sh` / `launch_task2.sh`), so profile changes relaunch only the stack; `launch_por.sh --real` refuses to start without a `mavros_node`, and `launch_task2.sh --real` also without the GPS forwarder (`--allow-no-gps-bridge` for a GPS wired to the Pixhawk), with `ROS_DOMAIN_ID` other than 40 (the DDS Router forwards `/system/*` only from the UUV domain; `--allow-other-domain` for a bench test) or with a `mavros_node` on another domain than the stack. The script `exec`s `<mavros prefix>/lib/mavros/mavros_node` directly: a launch `Node` action injects `-r __node:=mavros` which triggers mavlink/mavros#1977 (crashes on `CompanionProcessStatus`), and `ros2 run` orphans it on shutdown. Do not "fix" this or move MAVROS back into a launch file. `sitl.launch.py` starts only ArduSub SITL. `system_id: 255` in `mavros_config.yaml` is required for ArduSub to accept MANUAL_CONTROL.
- ArduPilot param names in this checkout are modern: `WP_SPD` (NOT `WPNAV_SPEED`), `WP_SPD_UP/DN`, `PILOT_SPEED_UP/DN`, `FS_EKF_ACTION`. Verify against `ArduSub/Parameters.cpp` / `libraries/AC_WPNav`. Curated file: `banyu_bringup/config/banyu_defaults.parm`, applied via `--defaults` (bare ardusub) and `--add-param-file=<path>` (sim_vehicle).
- ArduSub has no `MAV_CMD_DO_ORBIT`/autonomous CIRCLE — orbit must be hand-rolled tangent-velocity setpoints. Type-mask dispatch lives in `ArduSub/GCS_MAVLink_Sub.cpp` (`0xDF8` position-only → `guided_set_destination`, `0x5C7` velocity/yaw-rate → `guided_set_velocity`).
- GZ mesh resource paths depend on hooks: `banyu_simulation/hooks/gazebo_env.dsv` and `bluerov2_gz/hooks/setup.dsv` (`GZ_SIM_RESOURCE_PATH` incl. `share`) — don't drop them.
