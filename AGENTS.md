# AGENTS.md — BANYU_ROBOTX

ROS 2 Humble underwater ROV autonomy stack: ArduSub SITL + Gazebo Harmonic + MAVROS + BehaviorTree.CPP mission manager. Workspace root: `/home/gryd/Dev/ros2_ws_robotx`. ArduPilot source (non-ROS, read-only reference) lives at `/home/gryd/Dev/ardupilot_ws/ardupilot`.

## Architecture (non-obvious wiring)

- Packages: `banyu_bringup` (launch + config), `banyu_simulation` (worlds/models), `banyu_teleop` (gamepad → `mavros/manual_control/send`), `banyu_msgs` (`Detection.msg`), `banyu_mission` (BT mission manager), `banyu_detection` (**WIP — `por_detection` HSV/OpenCV detector; no finished target classifier yet**), `banyu_robocommand` (RoboCommand MQTT/protobuf bridge — the only **ament_python** package here).
- **`banyu_robocommand` cannot be run with `ros2 run`.** The vendored RoboNation schema is protobuf `edition = "2024"`: jammy's `python3-protobuf` 3.12.4 can't import it and `protoc` 31.1 can't regenerate it, so the node needs `protobuf==7.35` from the workspace venv (`./venv/bin/python -m banyu_robocommand.rc_bridge`). Never add a `protoc` step to colcon; re-vendor `gen/python` instead (`banyu_robocommand/rc_proto/VENDORED.md`). Competition rules forbid the *vehicle* connecting to the broker — this node is topside-only. See `banyu_robocommand/README.md` and `docs/robocommand-integration-research.md`.
- `proof_of_readiness.launch.py` is the main sim entrypoint: spawns `bluerov2_heavy` (from `model.xacro`, NOT `.urdf` — the install tree has a stale dangling `model.urdf` symlink, ignore it), `por_pool`, `Gate`, `yellow_buoy`, runs SITL + MAVROS + `banyu_mission`.
- Camera: gz topic `front_camera/image_raw` → `ros_gz_image image_bridge` → ROS `/front_camera/image_raw` (30 Hz). `camera/camera_info` is NOT bridged. Never modify the `front_camera` sensor block in `bluerov2_gz/models/bluerov2_heavy/model.xacro` — user-configured.
- Frames: Gazebo and MAVROS ROS pose/setpoint fields are **ENU** (`/mavros/local_position/pose` uses `frame_id: map`); MAVROS converts local `PositionTarget` fields to MAVLink NED internally. The `coordinate_frame` constants are still MAVLink values. Convert mission NED offsets explicitly: east→ROS x, north→ROS y, down→negative ROS z.
- **Navigation is velocity-loop, not position-setpoint.** ArduSub GUIDED `0xDF8` position targets go through AC_WPNav, which in this SITL setup crawls and lets depth drift — verified empirically. `NavToGate`/`ReturnToStart` instead run a P-controller on pose error and stream velocity-only setpoints (`type_mask 0xDC7`, ROS ENU components, gains `nav_kp_h/v`, caps `nav_max_speed_h/v`). Velocity-only control holds depth precisely. Keep `0xDF8` for reference only.
- **Every setpoint must carry an explicit zero yaw rate** (type_mask clears IGNORE_YAW_RATE, `yaw_rate = 0`). ArduSub persists `yaw_look_at_heading_slew` from the last commanded yaw rate and applies it in the guided-velocity LOOK_AT_HEADING branch, so a setpoint that merely ignores yaw rate leaves the vehicle rotating toward heading 0. `bodyVelocityYawRateSetpoint` overrides the field for turns/orbits.
- `NavToGate` defaults dive in place: `gate_offset_east=0`, `gate_offset_down=2.0` (NED offsets). The sub spawns 3 m behind the gate, so horizontal movement here would put it above the gate and collide on descent. Forward motion belongs to `GatePass`.
- ArduSub accepts `setpoint_raw/local` **only in GUIDED**, and setpoints must stream continuously (~10–50 Hz), not once. When the sim misbehaves, check for stale processes: `sim_vehicle.py`'s `ardusub` child and `mavproxy` can outlive their launch (orphaned from old terminals); a clean test requires killing ALL of them first or the new `ardusub` fails to bind port 5501 and the gz plugin logs `ArduPilot controller has reset`.
- Ports: MAVROS on `udp://127.0.0.1:14551`, SITL exports `14550` for QGC (works fine as a second GCS). In GUIDED, ArduSub ignores MANUAL_CONTROL RC overrides, so teleop's abort role is mode-switch only.
- Setpieces: Gate at x≈−4 (posts Y=±1), `yellow_buoy` at x≈6 z≈−2.1, sub spawns (−7, 0, −2). `mav.parm` at workspace root is an auto-dumped param reference.

## Build / run (shell is zsh!)

- ROS `setup.bash` uses `BASH_SOURCE`, which is unset in zsh → sourcing it resolves the prefix to CWD and errors. Always run ROS commands via: `bash -c 'source /opt/ros/humble/setup.bash && source install/setup.bash && <cmd>'` (from workspace root; install is symlink-install).
- Focused build: `colcon build --packages-select banyu_msgs banyu_mission banyu_detection` (from workspace root). Build `banyu_msgs` before dependents.
- No unit tests; only `ament_lint_auto` (copyright/cpplint disabled in every CMakeLists — keep that pattern).
- Launch-description sanity check without booting sim: `ros2 launch banyu_bringup proof_of_readiness.launch.py --show-args`.

## Mission manager gotchas (`banyu_mission`)

- Uses **core `behaviortree_cpp` 4.9.0 only** (apt `ros-humble-behaviortree-cpp`; headers at `/opt/ros/humble/include/behaviortree_cpp`). `behaviortree_ros2` is NOT packaged for Humble and unnecessary here — do not add it.
- BT4 API differs from v3: `NodeStatus` is `enum class`; `BehaviorTreeFactory` has **no `setup()`**; register with `factory.registerNodeType<T>("ID", extraArgs...)`; run via `tree.tickWhileRunning()` in a `std::thread`; Groot2 monitor via `Groot2Publisher` (default port param 1666).
- `shared_from_this()` in the ctor throws `bad_weak_ptr` — `BanyuMission` uses two-phase init: `main()` calls `node->initialize()` after `std::make_shared`.
- Tree `bt/mission_tree.xml`: `ReactiveFallback[AbortedOrTeleop | Sequence[MissionActive→NavToGate→GateAlign→GatePass→SearchMarker→MarkerAlign→MarkerOrbit→ReturnToStart]]`. All phases are implemented: `NavToGate` dives in place, `GateAlign`/`MarkerAlign` are body-frame visual servoing (`VisualAlign` base, `gate_align_*`/`marker_align_*` params), `GatePass` drives forward until distance/detection-loss, `SearchMarker` sweeps and then **approaches to `search_approach_distance` (2.5 m)** using `detection.distance` while keeping the buoy centered with `marker_align_*` gains (if the detection is lost mid-approach it holds position, not forward), `MarkerOrbit` is a **strafe orbit**: body-y is the circle speed (`orbit_speed`), body-x locks the standoff range (`orbit_kp_range`/`orbit_radius_m`, default 3 m) so the sub never dives into the buoy, yaw rate (`orbit_kp_yaw`, sent via `bodyVelocityYawRateSetpoint`, which clears IGNORE_YAW_RATE and negates for mavros) keeps the buoy centered in frame, and completion is a **full revolution** by yaw integration (|Δyaw| ≥ `orbit_angle_rad`); the **return leg** (`ReturnToStart` is a nested Sequence) does `TurnAround` (yaw-rate turn — rotates at `turn_yaw_rate` until the gate is sighted, then switches to **closed-loop yaw capture** on `offset_x` (`turn_capture_gain`, stop at `turn_capture_deadband`) so momentum can't swing the gate out of frame; 180° is only the cap. The capture uses the **same `+kp·offset_x` sign as the MarkerOrbit yaw-follow**, which is the empirically converging convention) → `SearchGate` (sweep until gate detected) → `GateAlign` (center on gate) → `ReturnGatePass` (forward while centering, tracks min distance; when the gate leaves the frame after being seen within `gate_pass_lost_distance`, pushes blindly `gate_pass_clearance_m` **beyond the loss distance** — `loss + clearance`, so the sub's rear clears the gate plane regardless of where detection was lost) → `Surface` (ascend to `surface_depth`). `AbortedOrTeleop` only reacts to the `/banyu/mission/abort` service — auto-abort on mode-change/takeback is a known gap.
- **Do NOT use `ReactiveSequence` for the phase chain.** BT 4.9 `StatefulActionNode::tick()` calls only `onStart()` on the first tick and `onRunning()` on later ticks; `ReactiveSequence` re-ticks from the first child every tick and halts non-running siblings, so any action after the first never reaches `onRunning` and the chain loops forever (verified with a standalone BT test: `NavToGate.onRunning` fired 100×, `GateAlign.onRunning` 0×). Plain `Sequence` (memory of the running child) works — abort reactivity is provided by the root `ReactiveFallback`, which halts the branch when `AbortedOrTeleop` succeeds.
- BT nodes don't use blackboard for data flow; they share a mutex-protected `MissionContext` (pose/state/detection). `/banyu/detection` contract: one best Detection per frame; `object_id` 0=gate, 1=yellow buoy; `offset_x/y` normalized ±1, +y = image-down.

## Repo-specific build/launch traps

- `banyu_msgs/package.xml`: `<member_of_group>rosidl_interface_packages</member_of_group>` must be a **top-level** element, NOT inside `<export>` — Humble's `package_xml_2_cmake.py` only fills `MEMBER_OF_GROUPS` from top level, otherwise `rosidl_generate_interfaces` fails.
- `mavros_node` must be launched via `ExecuteProcess` (`ros2 run mavros mavros_node`) — a launch `Node` action injects `-r __node:=mavros` which triggers mavlink/mavros#1977 (crashes on `CompanionProcessStatus`). Do not "fix" this. `system_id: 255` in `mavros_config.yaml` is required for ArduSub to accept MANUAL_CONTROL.
- ArduPilot param names in this checkout are modern: `WP_SPD` (NOT `WPNAV_SPEED`), `WP_SPD_UP/DN`, `PILOT_SPEED_UP/DN`, `FS_EKF_ACTION`. Verify against `ArduSub/Parameters.cpp` / `libraries/AC_WPNav`. Curated file: `banyu_bringup/config/banyu_defaults.parm`, applied via `--defaults` (bare ardusub) and `--add-param-file=<path>` (sim_vehicle).
- ArduSub has no `MAV_CMD_DO_ORBIT`/autonomous CIRCLE — orbit must be hand-rolled tangent-velocity setpoints. Type-mask dispatch lives in `ArduSub/GCS_MAVLink_Sub.cpp` (`0xDF8` position-only → `guided_set_destination`, `0xDC7` velocity-only → `guided_set_velocity`).
- GZ mesh resource paths depend on hooks: `banyu_simulation/hooks/gazebo_env.dsv` and `bluerov2_gz/hooks/setup.dsv` (`GZ_SIM_RESOURCE_PATH` incl. `share`) — don't drop them.
